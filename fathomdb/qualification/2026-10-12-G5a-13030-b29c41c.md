### Finding F-G5a-1: the fork's NVRTC test uses PTX, not CUBIN

CF-AC-04c says the fork's own NVRTC-dependent tests compile to CUBIN for
sm_86, so they need no PTX JIT and must pass on G5a. The only such test,
`drops_after_a_sticky_error_neither_panic_nor_abort`, calls
`crate::nvrtc::compile_ptx` and `ctx.load_module(ptx)`
(`src/driver/safe/core.rs` ~5766), so on G5a its child fails at
`core.rs:5773:47` with `CUDA_ERROR_UNSUPPORTED_PTX_VERSION` (all three runs,
every 13.1+ build). The catalogue lists the test for G1 and G5b only, so the
test plan and the requirement disagree. It is recorded UNMEASURED here, not
passed, and needs a disposition (change the test to CUBIN, or amend
CF-AC-04c).

### Baseline-vs-`C` differences (explained against the maps)

- **The baseline loaded CUDA 12.6, not the 13.x wheels.** With the same
  `LD_LIBRARY_PATH`, `ec1cac71` tried the unversioned names first, which
  the loader cache resolves to the system 12.6 `libcublas`,
  `libcublasLt`, `libcurand` and `libnvrtc`. `C` loaded the venv's
  `libcublas.so.13`, `libcublasLt.so.13`, `libcurand.so.10` and
  `libnvrtc.so.13` (maps below). Item 9 (CF-REQ-11) intends this.
- **Consequence for the UNMEASURED tests:** at the baseline they pass in
  every run, because NVRTC 12.6's PTX is JIT-able by driver 580; at `C`
  they fail in every run with the PTX error above. By CF-REQ-12's pattern
  alone this would read "regression"; the maps show the cause is the
  library each build loaded (12.6 at the baseline, 13.3 at `C`), which is the
  driver-580 limit CF-AC-04c names, not a change in the code under test.
  They are therefore recorded UNMEASURED for G5b, not passed and not
  dismissed.
- `libnvidia-ptxjitcompiler.so.580.178.04` is mapped only at `C`: the
  driver loads the JIT compiler to try (and reject) the new PTX.
- Fork tests have no baseline.
- Baseline main runs: 69 upstream names (test plan § 2.1), all pass
  except the host-dependent test.
